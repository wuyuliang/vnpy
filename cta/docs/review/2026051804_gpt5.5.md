## 2. 总体结论

当前系统已经完成了从规则候选、特征拼接、三类模型、组合约束、OOT 报告到 live 入口的主链路雏形，这是非常有价值的基础。但现在最需要先收敛的是“可信度工程”：防止未来函数、过拟合、模型门控不可解释、OOT 成交细节缺失，以及真实期货资金约束不够严格。

建议下一阶段不要继续堆新模型或新特征，优先把以下四件事做扎实：

- 让所有运行时核心逻辑回到正常 `.py` 模块，禁止通过 `.py.txt` 和 `exec()` 绕过重构、测试、静态检查。
- 建立严格的特征因果审计，尤其修复 price action swing 类特征的未来确认泄露。
- 重做 final decision stacking 的训练方式，使用 out-of-fold 训练元模型，避免在训练集上用基模型原地预测。
- OOT 输出完整候选漏斗和真实期货成交明细，包括模型过滤失败的候选、真实合约乘数、手数取整、保证金、现金约束与逐笔权益变化。

- `rg "exec\(" cta/model` 不再命中运行时加载核心逻辑。

- 每个拆分后的业务模块少于 500 行。

### P0.2 修复 price action swing 特征的未来函数

位置：

- `cta/feature/price_action_swings.py:43`
- `cta/feature/price_action_swings.py:61`
- `cta/feature/price_action_swings.py:79`

问题：

`swing_high()` 和 `swing_low()` 使用 `i + j` 的右侧未来 K 线判断当前 K 是否为 swing，但函数把 swing 值直接写在当前索引 `i`。随后 `dist_to_last_swing_*()` 立即 `ffill()`，等于在 pivot 当根 K 就知道了未来 `right` 根 K 后才能确认的信息。

本地最小证据：

```python
swing_high(pd.Series([1, 2, 5, 2, 1]), left=2, right=2).tolist()
# [nan, nan, 5.0, nan, nan]
```

在真实交易中，索引 2 的 swing high 最早要到索引 4 才能确认。

建议修改：

- swing 值写入 `i + right`，或额外输出 `confirmed_at` 并在特征表 merge 时只使用确认后的值。
- 将相关特征命名为 `*_confirmed`，避免和即时可见特征混淆。
- 在 causality manifest 中将旧 swing 特征标记为不可用，修复后再改为 causal。
- 增加单测：pivot 当根不可见，`right` 根之后才可见。

验收标准：

- `swing_high([1,2,5,2,1], left=2, right=2)` 的确认值不应出现在第 3 根，而应出现在第 5 根。
- OOT 报告中不再出现未审计或明显未来确认的 swing 特征。

### P0.3 final decision stacking 存在训练集原地预测过拟合

位置：

- `cta/model/pipeline_orchestrator_source.py.txt:2471`
- `cta/model/pipeline_orchestrator_source.py.txt:2528`
- `cta/model/final_decision_model.py:71`

问题：

当前 final decision meta model 的训练特征来自基模型对训练集自身的预测。例如 trade filter、regime、MFE/MAE 模型先在 train 上训练，再对同一份 train 预测，随后这些预测被用于训练 final decision model。这会让 meta model 看到过于乐观的基模型分数。

同时 `final_decision_model.py` 的 `_quick_cv_auc()` 文档写“time-aware”，但实际使用 `KFold(..., shuffle=True)`，这对时间序列不安全。

建议修改：

- 对 train 切分 walk-forward 或 `TimeSeriesSplit`，生成 out-of-fold base predictions 作为 meta_train。
- valid/test/OOT 只能用已经训练好的基模型向前预测，不得回看。
- final decision model 也纳入 train/valid AUC gap 约束，例如沿用当前 3% 上限。
- 将 `_quick_cv_auc()` 改为 `TimeSeriesSplit`，或改名为非时间序列 CV 并禁止在时序训练中使用。

验收标准：

- meta_train 中每一行的基模型分数都来自未训练过该行标签的 fold 模型。
- final decision report 中输出 train、valid、test、OOT 的 AUC/gap。
- 删除或更正 “shuffled KFold 是 time-aware” 的文档和注释。

### P0.4 live 模型过滤不应默认 fail-open

位置：

- `cta/live/model_filter.py:108`
- `cta/live/online_feature.py:71`

问题：

`ModelSignalFilter.should_allow_order()` 在缺特征、特征 provider 报错、预测报错、特征列缺失、特征为空时都返回 `True`。这适合早期调试，但不适合真实交易。  
此外 `OnlineFeatureLoader` 的 day 路径假设是 `root/day/{symbol}.parquet`，但当前实际特征文件布局更接近 `cta/data/feature/day/RB0/YYYY-MM-DD.parquet`，测试仍在验证旧单文件布局。

建议修改：

- 增加配置 `fail_open` 或 `mode`，live 默认 fail-closed，sim/dryrun 可配置 fail-open。
- `should_allow_order()` 返回结构化结果，例如 `allow`、`reason`、`missing_features`、`model_version`。
- 修复 `OnlineFeatureLoader` 支持分区目录，按 `symbol/date.parquet` 加载最近可用特征。
- 更新 live 测试，不再只覆盖旧布局。

验收标准：

- live 模式缺模型或缺特征时默认拒单，并记录明确原因。
- day 和 minute60 的在线特征路径都能读取当前真实布局。

### P0.5 OOT trade detail 没有完整记录模型过滤失败的候选

位置：

- `cta/model/pipeline_oot_evaluation_source.py.txt`
- 最近报告：`cta/report/backtest/20260517_POOL_day_both_model_pipeline/20260517_POOL_day_both_oot_summary.csv`

问题：

最近 POOL day OOT 中有候选和 executed 样本，但 `selected_rows=0` 且 trade detail 为空。原因是模型 gate 之前的候选被过滤掉后，没有以 `blocked_model_gate` 形式进入逐笔明细。这样无法回答“为什么没有成交”，也无法复盘阈值是否过严。

建议修改：

- OOT 输出应包含所有 OOT 候选，每一行都有 `execution_status`。
- 增加模型门控 block reason，例如 `blocked_trade_filter`、`blocked_regime_gate`、`blocked_mfe_mae_gate`、`blocked_final_decision_gate`。
- trade detail 与 summary 均输出漏斗：candidate、model_selected、risk_allowed、portfolio_allowed、executed、closed。
- 对每个 block reason 输出数量、占比、按 symbol/group/signal_type 拆分。

验收标准：

- 即使没有成交，`oot_trade_details.csv` 也能看到全部候选及被过滤原因。
- `summary.csv` 中的 candidate 数、selected 数、blocked 数与 detail 行数一致。

## 4. P1 重要改进

### P1.1 walk-forward 窗口样本量太小，指标不可置信

证据：

`20260517_POOL_day_both_metrics.csv` 抽查显示：

- train 行数 32，单窗口样本中位数约 20.5。
- valid 行数 32，单窗口样本中位数约 2。
- test 行数 32，单窗口样本中位数约 3.5。
- `selection_valid_auc` 有 78/96 行为空。

问题：

按 `signal_type`、group、interval 继续细分后，很多窗口没有足够样本训练或验证。此时 AUC、IC、decile return 很容易被少数样本支配。

建议修改：

- 增加 `min_train_samples`、`min_valid_samples`、`min_test_samples` 的硬门槛。
- 样本不足时回退到 group 级或 all-signal 级模型，而不是继续训练细分模型。
- report 中标记 `insufficient_sample`，并禁止把该窗口作为有效模型选择依据。

### P1.2 causality manifest 覆盖率不足

证据：

当前 `20260517_POOL_day_both_unaudited_features.csv` 有 434 个未审计特征，`causality_manifest.csv` 只有少量特征记录。

问题：

模型特征数量已经较多，但因果可用性审计覆盖不足。只靠 blacklist 很难避免“名字正常但计算穿越”的特征进入训练。

建议修改：

- 所有 `feature_*`、`generic_*`、`feature_model_*` 均要求进入 manifest。
- 未审计特征超过阈值时，训练直接失败或降级为只使用已审计特征。
- 报告中输出未审计特征 TopN、使用频率、重要度、是否进入 top10。

### P1.3 OOT 期货仓位需要合约乘数与手数取整

位置：

- `cta/model/pipeline_oot_evaluation_source.py.txt`
- `cta/config/model_oot_eval_config.py`

问题：

当前 OOT 里 `position_qty = notional / entry_price` 更像现货数量，不是期货手数。中国商品期货需要使用合约乘数、最小交易手数、保证金率、手续费、滑点与价格跳动。

建议修改：

- 增加或复用 per-symbol 合约配置：`contract_size`、`price_tick`、`lot_size`、`margin_rate`、`commission`。
- 手数计算：`lots = floor(target_notional / (entry_price * contract_size * lot_size)) * lot_size`。
- 保证金计算：`margin = lots * entry_price * contract_size * margin_rate`。
- 若 `lots <= 0`，输出 `blocked_zero_lot`。
- trade detail 中明确区分 `entry_notional`、`entry_margin`、`cash_used`、`available_cash_after_entry`。

### P1.4 OOT 拆分模块仍是 placeholder

位置：

- `cta/model/oot_position_sizing.py`
- `cta/model/oot_gates.py`
- `cta/model/oot_portfolio_constraints.py`
- `cta/model/oot_trade_simulation.py`

问题：

这些文件目前主要是 compatibility scaffold，真实逻辑仍在 source txt 中。模块拆分测试只验证 import 或表层契约，不能覆盖数值正确性。

建议修改：

- 将 gate、sizing、portfolio constraint、trade simulation 真实逻辑迁入对应模块。
- 每个模块增加 2 到 3 个数值单测，例如：
  - 模型阈值刚好等于阈值时是否通过。
  - 单笔最大亏损 0.1% 时手数和保证金是否正确。
  - 现金不足时是否拒单。
  - 周回撤达到阈值时是否阻断新仓。

### P1.5 测试兼容 shim 导致重复收集

位置：

- `cta/model/feature/tests/test_candidate_training_dataset.py`

问题：

该文件通过 import part01/part02/part03 保持兼容，但 pytest 同时也直接收集 part 文件，造成重复测试。短期不是功能 bug，但会拖慢 CI 并让测试数量虚高。

建议修改：

- 兼容期结束后删除 shim，或将文件改名为非 `test_`。
- 若必须保留，设置 `__test__ = False` 并确保外部 import 不被 pytest 收集为测试用例。

## 5. P2 架构和工程质量建议

### P2.1 不建议把 `.claude/worktrees` 放在 `cta/` 内

当前 `cta/.claude/worktrees` 存在大量文件，包括非 CTA 目录结构和嵌套 `.git`。这会污染扫描、统计、review 与上下文检索，也容易误触 AGENTS 的“只改 cta”边界。

建议将 assistant worktree 移到仓库外，或至少加入明确 ignore，并让所有 line-limit 和 code review 脚本默认跳过。

### P2.2 calendar 特征应避免依赖下一行数据

位置：

- `cta/feature/calendar_feat.py`

`is_week_end`、`is_month_end` 使用 `shift(-1)` 判断下一行日期。虽然日历本身通常是可提前知道的信息，但更稳妥的做法是使用交易日历或自然日历函数计算，避免在审计中被误判为未来数据依赖。

### P2.3 文档需要区分“设计完成”和“实现完成”

`cta/model/model.md` 与 refactor 文档中已经描述了模块化方向，但当前实现仍有 source txt shim 和 placeholder 模块。建议在文档里明确当前状态：

- 已完成：外部接口与部分测试契约。
- 未完成：真实逻辑完全迁移、数值单测、删除 source txt。

## 6. 策略研究建议

### 6.1 先暂停追逐过高 OOT，回到可解释漏斗

如果某些 OOT 收益异常好，优先假设存在执行假设偏乐观、特征泄露、样本量过小或模型选择偏差。建议先建立可解释漏斗：

1. 规则候选：所有候选机会，不带模型过滤。
2. 交易标签：是否真实触发、MFE、MAE、持有期收益。
3. 模型过滤：trade filter、regime、MFE/MAE、final decision 每一步的通过率。
4. 风控过滤：现金、保证金、单笔亏损、日/周回撤、组合集中度。
5. 实际成交：成交时间、成交价、手数、保证金、止损线、退出原因、净值影响。

只有每一层的行数和收益都能解释，OOT 结果才值得用来指导策略。

### 6.2 生产优先使用简单模型链路

短期建议不要把四层 stack 全部直接用于实盘。更稳妥的生产候选：

- 第一版：baseline rule + calibrated trade filter + regime hard gate + portfolio allocator。
- 第二版：加入 MFE/MAE 作为仓位或止盈止损调参，不直接作为是否开仓的唯一条件。
- 第三版：只有当 OOF stacking 通过长期稳定验证后，再启用 final decision stack。

### 6.3 day 与 minute60 分开治理

day 和 minute60 的信号结构、成交假设、止损触发粒度、HTF/LTF 关系不同。建议：

- day 模型和 minute60 模型分开训练、分开评估、分开阈值。
- minute60 可以读取 day 趋势作为 HTF 特征。
- day 不应因为缺少更高周期而默认 `htf_missing`，应有独立的 day-level gate 逻辑。

### 6.4 group pool 需要样本门槛和部署路由

按品种 group 训练是正确方向，但需要防止“披着 pool 的小样本模型”：

- 每个 group 至少有 `min_used_symbols`。
- 每个 signal_type 至少有 `min_train/valid/test samples`。
- 报告输出 group、symbol、signal_type 的样本和收益贡献。
- 上线模型必须保存 routing manifest：symbol -> group -> interval -> model_version。

- 测试兼容 shim 重复收集。

## 11. 结论

这个 CTA 项目的方向是对的：先把规则候选、特征、模型、组合风控、报告和 live 链路串起来，再逐层提高真实性。但当前最需要的不是更多模型，而是把“可信 OOT”建起来。

建议下一步优先修 P0，尤其是未来函数、OOF stacking、OOT 候选漏斗和真实期货资金约束。等这些底座可靠后，再讨论策略收益的优劣，结论会更硬，也更适合迁移到服务器和仿真交易。
