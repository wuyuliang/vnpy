## 2. 优点（做对的地方）

1. **默认值零漂移**：三杠杆默认值与 `usage_pct.md §11.3` 完全一致——
   size `2.0/1.5/1.0/0.7/0.4/0.5/0.3`；max_concurrent `6/5/3/2/3/2/1`；pctl_delta `-5/-3/0/+5/+15/+12/+20`；
   raw_delta 同向缩放 `-0.03/-0.02/0/+0.03/+0.10/+0.08/+0.12`。
2. **并发账务平衡无泄漏**：`signal_type_open_counts` 在 position dict 存 `signal_type`（L486）、开仓 +1（L488）、
   盘中平仓 -1（L306-310）、收尾清算 -1（L490-495），三处均 `max(0,·)` clamp + 归零 `pop`，开/平守恒。
3. **gate delta 稳健**：percentile 模式 `clip(0,100)`、raw 模式 `clip(0,1)`，均 fail-open
   （`getattr(cfg, …, {})` + `map` 缺省 0.0），未配置 signal_type 不受影响。
4. **config 规范统一**：三 dict 全部 `field(default_factory=…)` + `__post_init__` 内 `_check` 区间校验
   + 键 `.strip().lower()` 归一化 + `MappingProxyType` 冻结，与既有 `commission_pct_by_cluster_interval` 范式一致。
5. **拦截链位置正确**：signal_type 并发检查在 elif 链中位于 `max_concurrent_positions_total` 之后、
   `blocked_symbol_concurrent` 之前（L428），受 `use_portfolio_constraints` 总开关控制，可一键关闭。
6. **新 block_reason 完整接线**：`BR_BLOCKED_SIGNAL_TYPE_CONCURRENT` 常量 + 列表 + `__all__` 三处注册齐全。
7. **风控 scaler 安全默认**：`SignalTypePositionScaler` 经 `enable_signal_type_size_scaler=False` 默认关闭，
   不改动现有 sim/live 行为；自身有单测覆盖。

  2. `test_model_pipeline_part01.py::test_evaluate_oot_real_execution_adds_position_sizing_fields`
  3. `test_model_pipeline_part01.py::test_evaluate_oot_real_execution_intrabar_stop_tracking`
  4. `test_model_pipeline_part01.py::test_evaluate_oot_real_execution_numeric_correctness`
  5. `test_model_pipeline_part02.py::test_evaluate_oot_real_execution_intrabar_trailing_stop_tracking`
  6. `test_model_pipeline_part04.py::test_evaluate_oot_real_execution_applies_roll_cost`
  7. `test_model_pipeline_part04.py::test_evaluate_oot_real_execution_symbol_concurrent_cap_blocks_fourth_entry`
  8. `test_model_pipeline_part06.py::test_evaluate_oot_real_execution_monthly_dd_hard_stop`

  典型两例：

    期望第 4 笔被 `blocked_symbol_concurrent`（=1），实际 **0**——因 atr `max_concurrent=3` 先触发

  "无 signal_type 差异化"假设下写的硬编码数值/拦截断言，实现时**未跑全量 pipeline 测试并同步解耦**。

### H2 — eval-only pipeline 不强制名义敞口 cap（cluster_notional_pct / total_notional_pct 失守）
- **现象（v10 实测）**：在 `oot_20260531_163014_cluster_both_sigtype_v10_target` 上重建 cluster_index 仓位曲线
  （事件法 +1/-1 over `[entry_fill_datetime, final_exit_datetime]`），2024-09-24 ~ 2024-10-08：
  - cluster_index 并发笔数峰值 **7**（@ 09-25 11:30 / 09-27 14:00 / 10-08 09:30）；
  - cluster_index notional 峰值 **$8.42M ≈ 起始资金 84.2%**（@ 09-27 14:00），自 09-25 11:30 起就一直
    高于 50%，直到 10-08 批量 horizon_exit 才回落；
  - 全局 7 个 cluster 加总在同窗口峰值 **~$57.9M ≈ 起始资金 579%**（@ 09-30 15:00），41 个并发持仓。
- **位置**：
  - `cta/model/oot/pipeline_oot_evaluation.py` 的 portfolio_constraints 拦截链只有 **笔数维度**：
    `max_concurrent_positions_total` / `max_total_per_cluster` / `max_per_symbol` / `max_signal_type_concurrent`，
    **未检查** `max_cluster_notional_pct` / `max_total_notional_pct`；
  - 名义占比 cap 仅在 `cta/portfolio_logic/opportunity_ranker.py` L136-138 强制（`symbol_cap` / `cluster_cap`
    / `total_cap`），但 eval-only 路径不走 ranker。
- **配置侧诱因**：`cfg_sigtype_target_v10.json` 显式抬高 `max_concurrent_positions_total=20` /
  `max_concurrent_positions_per_symbol=5` / `max_symbol_notional_pct=0.40`，但未 override
  `max_cluster_notional_pct` / `max_total_notional_pct` / `max_total_per_cluster`——而这三项的默认强制点
  恰好都不在 eval pipeline 上。
- **影响（H 级）**：
  - v10 OOT 报告的 PnL / 回撤 / Sharpe **不能视为"经风控约束的真实仓位曲线"**；同一份预测换成 sim/live 的
    lots×scaler 路径后，因名义敞口被压回 50%/150%，实际可达 PnL 将系统性低于 OOT 报告；
  - 直接违反 CLAUDE.local.md"OOT/仿真/真实交易逻辑一致"红线；
  - 与 M2（三层一致性）形成放大效应：杠杆2/3 在 OOT 生效但 sim/live 缺位，叠加 notional cap 缺位，
    OOT 与实盘曲线背离会被双重放大。
- **建议**：
  1. 在 `pipeline_oot_evaluation` 的入场前置 cap 链追加 **cluster_notional_cap / total_notional_cap** 检查
     （equity-as-of-bar 做分母，与 ranker 同口径）；分别新增 `BR_BLOCKED_CLUSTER_NOTIONAL` /
     `BR_BLOCKED_TOTAL_NOTIONAL` 拦截原因，与 ranker 路径共用常量；
  2. 或者把 eval-only 路径统一走 `opportunity_ranker.allocate` 撮合（与 sim/live 共代码），但工程量更大；
  3. 配置侧：v10 cfg 显式补 `max_cluster_notional_pct` / `max_total_notional_pct` override，避免后续靠默认值"以为有保护"；
  4. 修复后必须重跑 v10 OOT，预期：cluster_index 09-25 11:30 后的 IC0 / 部分 IF0 加仓被名义 cap 拦截，
    9-27 / 10-08 的 PnL 显著下修；汇总到 `cta/report/change_log.md`。

### M1 — sizing 系数是"天花板"而非"真乘数"
- **现象/位置**：`pipeline_oot_evaluation.py` L398 `position_scale = min(eff_pos_cap, max_single_loss_pct/expected_loss_pct)`，
  其中 `eff_pos_cap = max_position_scale × mult`。
- **影响**：`mult>1`（放大）仅对"风险反推已顶到 `max_position_scale`"的交易生效；对风险反推本就低于天花板的交易是
  **no-op**。`mult<1`（缩量）则总是生效。即"放大 pullback"是**有条件的**，"缩小 atr"是无条件的（此前已向用户解释）。
- **建议**：在 `usage_pct.md` 明确该语义；若需无条件放大，改为 `min(risk_based, max_position_scale) × mult` 再夹硬上限，
  并重跑对比（会改变收益/风险，需重新验证）。

### M2 — 三层一致性缺口（最重要，实盘前必做）
- **现象**：杠杆2（`signal_type_max_concurrent_positions`）与杠杆3（`trade_filter_*_threshold_delta_by_signal_type`）
  **仅在 OOT 路径生效**；sim/live 走 `cta/risk/orchestrator` 的 lots×scaler 模型，**无等价件**。杠杆1 的
  `SignalTypePositionScaler` 虽存在但 `default-OFF`。
- **影响**：若按当前 OOT 默认上线，实盘不会施加并发上限/阈值 delta/size 系数 → **违反"OOT=sim=live 同 cfg 同代码"铁律**，
  实盘成交与回测系统性偏离。
- **建议**：实盘前在 `cta/risk/guards` 增 per-signal_type 并发 guard + 在线阈值叠加器，并把 size scaler 经 soak 后 default-on；
  cfg_fingerprint 三处比对纳入这三个字段。

### M3 — ranker 不感知 signal_type 并发 cap
- **现象/位置**：cap 只在 pipeline portfolio_constraints 循环强制；`opportunity_ranker.allocate` /
  `PortfolioState` 仅跟踪 symbol/cluster 的 tentative/commit 计数，无 signal_type 维度。
- **影响**：ranker 可能把有限槽位分配给某 signal_type，随后该笔在 pipeline 被 `blocked_signal_type_concurrent` 拦掉，
  且不会回补次优候选 → **槽位浪费**（效率损失，非正确性 bug）。
- **建议**：把 signal_type 计数纳入 `PortfolioState` 的 tentative/commit，使 ranker 预分配阶段即感知该 cap。

### M4 — 杠杆2 运行时拦截缺专门单测
- **现象**：`test_model_oot_eval_config.py` 覆盖了三个 dict 的默认值/归一化/越界校验，但 **pipeline 的
  `blocked_signal_type_concurrent` 实际拦截行为无断言**。
- **影响**：并发账务/拦截一旦回归（如 add-layer 计数 bug），现有测试发现不了。
- **建议**：补一条 pipeline 测试——构造同 signal_type、同时在仓超过 `max_concurrent` 的候选，断言第 N+1 笔
  `block_reason == "blocked_signal_type_concurrent"`，并验证平仓后计数回落、后续可再开。

### M5 — pyramid add-layer 计数风险
- **现象/位置**：L488 对所有执行入场（含 `is_add_layer=True`）都 `signal_type_open_counts += 1`，而平仓按 pos 维度减计。
- **影响**：`use_pl_pyramid=True` 时同一 pos 的多个加仓 layer 会被多计入 signal_type 并发数 → 该 signal_type 偏紧、提前触顶。
  OOT 默认 pyramid 多为关，影响有限。
- **建议**：仅对非 add-layer（新开仓）计数，或加注释说明 layer 计入的预期；并在 M4 测试里覆盖 pyramid 分支。
