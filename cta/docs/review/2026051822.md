### 1.2 必修清单（before live 上线之前必须解决）

按本文章节编号，从优先级最高的 4 条 high 开始：

1. **H-§7.3 live vs portfolio_logic 风控解耦**：[live/risk.py](cta/live/risk.py) 实现的是按品种限单/限仓/限亏的简单规则；[portfolio_logic/risk_throttle.py](cta/portfolio_logic/risk_throttle.py) 实现的是 drawdown-aware 多级 throttle。两者**不共享任何代码**。OOT 评估走的是 portfolio_logic.RiskThrottle，但 live 走的是完全不同的 RiskGuard 规则栈 ⇒ OOT 看上去稳健不代表 live 稳健。**违反 CLAUDE.local.md 的"OOT / sim / live 一致性"硬约束**。详见 §7。
2. **H-§5.3 OpportunityRanker 配置漂移**：[opportunity_ranker.py:30](cta/portfolio_logic/opportunity_ranker.py:30) `self.interval_rank_weight = IntervalGateConfig().interval_rank` ⇒ 实例化默认 `IntervalGateConfig` 取 interval_rank，**完全忽略用户传入的 `pl_cfg.interval_gate.interval_rank`**。如果用户改了 `interval_rank` 默认权重，Ranker 仍按 day=1.0 / 60min=0.85 / ... 默认值计分。详见 §5。
3. **H-§4.4 leverage 口径语义模糊**：[pipeline_oot_evaluation.py:385](cta/model/pipeline_oot_evaluation.py:385) 的 `cap_lev = entry_equity * max_total_leverage - open_notional`，是按"原始 notional / equity"做杠杆 cap，**不是按"保证金占用 / equity"**。配置默认 `max_total_leverage=2.0` + `margin_rate=0.12`，意味着允许 notional 顶到 2× equity 时实际保证金占用仅 0.24× equity。变量名暗示真实杠杆但实际是名义杠杆。详见 §4。
4. **H-§2.4 horizon_i 近端截断引入标签分布漂移**：[baseline_candidate_gen.py:191](cta/strategy/baseline_candidate_gen.py:191) `horizon_i = min(len(frame) - 1, entry_i + hz)`，靠近数据末尾的 candidate 实际 lookforward 窗口比 hz 短 ⇒ MFE/MAE 标签分布偏向"无大行情"。训练集尾段的标签分布发生漂移。详见 §2。

### 1.4 跨模块隐患速览

- **离线 ↔ 在线 schema 一致性**：OOT 用 `feature_is_limit_up_close` / `feature_is_limit_down_close` 判涨跌停（[pipeline_oot_evaluation.py:122-130](cta/model/pipeline_oot_evaluation.py:122)），event-driven backtest 用 `_hit_price_limit` 自 OHLC 推断（[event_driven_backtest.py:24-50](cta/skills/data_backtest/event_driven_backtest.py:24)）。两套口径不互译。
- **margin_rate 来源**：[model_oot_eval_config.py:94](cta/config/model_oot_eval_config.py:94) 默认 0.12；[futures_meta.py](cta/config/futures_meta.py) 按品种存储 margin_rate；[pipeline_oot_evaluation.py:_resolve_contract_spec](cta/model/pipeline_oot_evaluation.py:61) 优先用 `symbol_contract_specs` 覆盖。但 `event_driven_backtest` 完全不用 margin_rate（只算 PnL，不算保证金）⇒ 回测层面看不到杠杆穿仓风险。
- **fallback_when_htf_missing="skip" 与 Fix-A/E 的耦合**：默认严格策略 `skip` 在单 interval 跑批时会触发 100% htf_missing，但 Fix-A/E 在 OOT 评估器里自动窄化 ⇒ 单 interval 跑批表面看不到 htf_missing 飙升。**风险**：Fix-A/E 只覆盖 `_evaluate_oot_real_execution` 这一个入口，**如果 live runtime 直接构造 HtfGate 而不过此入口，可能 100% htf_missing**。
- **stop_loss 一致性默认 off**：[model_oot_eval_config.py:136](cta/config/model_oot_eval_config.py:136) `enforce_stop_loss_consistency: bool = False`；`DEFAULT_OOT_EVAL_CONFIG` 显式设 True；但研究/测试场景的自建 config 容易忘改 True ⇒ 训练 label 与 OOT 执行口径漂移而无任何提示。

### 1.5 总体判断

主路径（OOF stacking、HTF gate、margin 占用/释放、trailing 方向、weekly/monthly peak 跨周月重置）**全部正确实现**。本轮未发现资金安全级别（C）缺陷。

但本轮发现的 4 条 H 都属于**"在长链路上的接口或口径漂移"**——单个模块独立测试都过，组合起来会引入隐患。这些是项目演化中典型的"知识债"：模块拆得越细，跨模块接口的隐式约定越脆。

下一阶段优先：补齐 OOT / live / sim 三层的统一风控测试 + 把 Ranker 等"由用户配置但默认值被静默覆盖"的入口加白盒测试。

### 2.3 发现的问题

#### H-2.4 horizon_i 近端截断引入标签分布偏移

- **位置**：[baseline_candidate_gen.py:191](cta/strategy/baseline_candidate_gen.py:191)
- **代码**：
  ```python
  horizon_i = min(len(frame) - 1, entry_i + hz)
  if horizon_i <= entry_i:
      continue
  ```
- **触发场景**：当 `entry_i + hz > len(frame) - 1` 时，`horizon_i` 被截断为 `len(frame) - 1`。靠近数据尾端 1-19 根的 candidate 都受影响（默认 `hz=20`）。MFE/MAE 计算窗口因此变短 ⇒ "大行情"被截断 ⇒ 标签偏向 `label_class=0`。
- **影响**：训练集尾段的标签分布与中段不一致；如果按 walk-forward 切分，最后一个 train window 末段、第一个 valid window 初段都受漂移影响。模型在 OOT 上的表现可能被低估或高估。
- **修法**（diff 草稿）：
  ```python
  # 当 horizon_i 被截断时 drop 该 candidate
  full_horizon_i = entry_i + hz
  if full_horizon_i > len(frame) - 1:
      continue   # 数据不够完整 horizon，drop 候选
  horizon_i = full_horizon_i
  ```
  或更宽容：保留但加 `is_horizon_truncated=1` 列，下游 dataset_prep 按需 drop。
- **配套测试**：`test_candidate_gen_drops_truncated_horizon`：用长度为 `len = 25 + hz`、`hz=20` 的 frame，断言 candidate 数量 ≤ `25 - hz` 而非 `25`。

#### M-2.5 exit_i 静默截断

- **位置**：[baseline_candidate_gen.py:65-67](cta/strategy/baseline_candidate_gen.py:65)
- **代码**：
  ```python
  if entry_i < 0 or exit_i < entry_i or entry_i >= len(frame):
      continue
  exit_i = min(exit_i, len(frame) - 1)
  ```
- **触发场景**：trade_log 中如果有 `exit_i > len(frame) - 1`，会被静默截断到末尾。同样会引入分布偏移，但比 §2.4 影响小（仅训练样本生成路径，不影响 candidate 生成）。
- **修法**：与 §2.4 同方向——加 `is_exit_truncated` flag 或直接 drop。

#### M-2.6 ATR warm-up 兜底逻辑切换计量单位

- **位置**：[baseline_candidate_gen.py:235-248](cta/strategy/baseline_candidate_gen.py:235)
- **代码**：
  ```python
  if np.isfinite(atr_entry) and atr_entry > 0:
      atr_v = atr_entry; atr_warmed = True
  elif np.isfinite(atr_signal) and atr_signal > 0:
      atr_v = atr_signal; atr_warmed = True
  else:
      hi_lo = entry_bar.high - entry_bar.low
      atr_v = hi_lo if ...
      atr_warmed = False
  ```
- **问题**：兜底用 `entry_bar.high - entry_bar.low` 作为 `atr_v`，但这是单根 bar 的 range，与 14 根 ATR 的尺度完全不同（差 14× 量级），导致 `mfe_atr / mae_atr` 在兜底路径上数值膨胀 14×。`atr_warmed=False` 列已标记，但下游训练代码是否真的按此列 drop 需要核对。
- **修法**：在 dataset_prep 阶段强制 `atr_warmed == 1` 才进入训练集；或者把兜底改为 NaN（不进入训练）。
- **配套测试**：`test_atr_unwarmed_samples_excluded_from_training`。

#### L-2.7 `cta_adapter` 缺少显式 docstring

- **位置**：[cta_adapter.py](cta/strategy/cta_adapter.py)
- **问题**：CLAUDE.local.md 要求每个策略文件顶部写"10 条策略要素"。`cta_adapter.py` 不是策略本体而是适配层，但因其落在 `strategy/` 下，按硬约束应有顶部说明（目标、与 vnpy 的接口约定、不可越界改的部分）。
- **修法**：补一段 module-level docstring。

### 3.3 发现的问题

#### M-3.1 swing_high/swing_low 用 Python 循环（性能）

- **位置**：[price_action_swings.py:43-78](cta/feature/price_action_swings.py:43)
- **代码**：双重 for 循环，O(n × (left+right))。
- **影响**：万级 bar 数据生成耗时数十秒；多品种批量时累计。但**功能正确**——明确把 swing 放到 `i + right` 索引位（[L58 注释](cta/feature/price_action_swings.py:58)），无 leakage。
- **修法**：向量化版本：
  ```python
  def swing_high(high, left=2, right=2):
      n = len(high)
      out = pd.Series(np.nan, index=high.index)
      h = high.values
      for k in range(left + right + 1):
          if k == left: continue
          # ...
      # 用 pd.Series.rolling + .max().shift() 组合实现，参考 pandas pivot pattern
  ```
  约 10× 提速。

#### M-3.2 causality_manifest 与 features 的同步未自动校验

- **位置**：[causality_manifest.csv](cta/feature/causality_manifest.csv) + [feature_compute_dispatch.py](cta/feature/feature_compute_dispatch.py)
- **问题**：新增 feature 时，[model/tools/generate_causality_manifest_seed.py](cta/model/tools/generate_causality_manifest_seed.py) 是手动跑的脚本。如果开发者忘跑，manifest 缺该 feature 的 causality 标注，但 pipeline 仍能正常跑——只是 leakage_audit 检查覆盖率会下降。
- **修法**：在 [run/tests/test_docs_sync.py](cta/run/tests/test_docs_sync.py) 风格的测试里加 `test_all_features_have_causality_manifest`：扫 `cta/data/feature/**/*.csv` 的 column 名 ∪ `cta/feature/*.py` 的输出列名 ⊆ manifest 行的 `feature_name`。
- **配套测试**：`test_causality_manifest_covers_all_features`。

#### L-3.3 `follow_through` 等组合特征在 OHLC 缺值时 silently 退化

- **位置**：[price_action_swings.py:199-208 follow_through](cta/feature/price_action_swings.py:199)
- **代码**：用 `np.sign(close - open).fillna(0)`。
- **问题**：fillna(0) 把 NaN 当作"无方向"。如果 close 缺失（数据 bug），特征值=0，模型会把它当作正常的"无方向 bar"训练，可能引入污染。
- **修法**：把 fillna(0) 改为 fillna(pd.NA)，下游训练统一处理 NaN。

### 4.3 发现的问题

#### H-4.4-A leverage 口径语义模糊

- **位置**：[pipeline_oot_evaluation.py:385](cta/model/pipeline_oot_evaluation.py:385) + [model_oot_eval_config.py:101-102](cta/config/model_oot_eval_config.py:101)
- **代码**：
  ```python
  cap_lev = max(0.0, float(entry_equity * float(cfg.max_total_leverage) - open_notional))
  ```
  配置注释："组合总杠杆上限：sum(open_notional) / equity <= max_total_leverage"
- **问题**：变量名 `max_total_leverage` 在期货语境下通常指"实际杠杆 = 名义本金 / 保证金"。但代码与注释明确口径是 `notional / equity`（**名义杠杆**）。`margin_rate=0.12` 时：
  - 名义杠杆 2.0 ⇒ 实际保证金占用 = 2 × 0.12 = 0.24 ⇒ 实际杠杆 ≈ 8.33×
  - 用户如果按"我想最多 2× 杠杆"配 `max_total_leverage=2.0`，实际会跑到 8.33× 杠杆
- **影响**：在压力测试下（cash 收缩 + margin call），实际敞口远超用户预期。这是**口径误解**型 bug，不是数学错误。
- **修法**（不改默认值，只加注释+测试+可选新字段）：
  ```python
  # 在 config 加：
  # 当 use_margin_weighted_leverage=True 时，cap_lev 改按
  # sum(notional * margin_rate) / equity <= max_total_leverage
  use_margin_weighted_leverage: bool = False  # 默认 False 保留向后兼容
  ```
  在 OOT 代码：
  ```python
  if getattr(cfg, "use_margin_weighted_leverage", False):
      cap_lev = max(0.0, (entry_equity * cfg.max_total_leverage - open_notional * margin_rate) / margin_rate)
  else:
      cap_lev = max(0.0, entry_equity * cfg.max_total_leverage - open_notional)
  ```
- **配套测试**：`test_max_total_leverage_notional_vs_margin_weighted`，覆盖两种口径下的实际敞口。
- **变更影响等级**：H（**实盘风险口径**，但默认值已存在多个版本，改默认会破坏 backtest 复现性）。

#### M-4.4-B exit_datetime 静默时间戳鉴定

- **位置**：[pipeline_oot_evaluation.py:99-101](cta/model/pipeline_oot_evaluation.py:99)
- **代码**：
  ```python
  non_increasing_exit = selected['exit_datetime'] <= selected['entry_datetime']
  if non_increasing_exit.any():
      selected.loc[non_increasing_exit, 'exit_datetime'] = selected.loc[non_increasing_exit, 'entry_datetime'] + pd.to_timedelta(1, unit='ns')
  ```

- **问题**：`exit <= entry` 的样本被静默推一纳秒以避开后续 `if exi < ent: continue`。如果上游 candidate_gen 生成了 `entry_i == exit_i`（horizon 不足），OOT 仍当成有效样本评估，等于把"无成交时间"误算成成交。
- **修法**：保留 fixup，但同时加 counter + logger.warning：
  ```python
  if non_increasing_exit.any():
      logger.warning(
          "OOT evaluator: %d rows had exit_datetime <= entry_datetime; "
          "pushed exit to entry+1ns. Check upstream candidate generation horizon coverage.",
          int(non_increasing_exit.sum()),
      )
      # 写入 summary 一列 `exit_time_fixup_rows`
  ```
- **配套测试**：`test_oot_logs_warning_when_exit_le_entry`。

#### M-4.4-C 涨跌停检测使用 signal bar 特征而非 entry bar

- **位置**：[pipeline_oot_evaluation.py:122-130, 344-346](cta/model/pipeline_oot_evaluation.py:122)

#### M-4.4-E PortfolioState 在 OOT 评估器里"手动重建"

#### M-5.4 RiskThrottle.apply_to_caps 不缩 notional cap

- **位置**：[model_oot_eval_config.py:100](cta/config/model_oot_eval_config.py:100) + [config.py:76-77](cta/portfolio_logic/config.py:76)
- **代码**：
  ```python
  @dataclass(frozen=True)
  class OotEvaluationConfig:
      symbol_contract_specs: dict[str, dict[str, float]] = field(default_factory=dict)
  ```
- **问题**：`frozen=True` 只阻止 top-level attribute reassign，不阻止 nested dict mutate。用户可以 `cfg.symbol_contract_specs["RB0"] = {...}`，dict 引用本身没换，frozen 不报错。两个 `OotEvaluationConfig` 实例共享同一 default_factory 产生的 dict（实际不会，因为 default_factory 每次调用都生成新 dict——这一点 Python 的 dataclasses 已经处理对了，✅）。但**实例内部的 dict 仍可被外部代码原地修改**。
- **修法**：把 dict 字段改为 `types.MappingProxyType(...)` 或 `frozenset`/`tuple of pairs`，或者在 `__post_init__` 中转换。
- **配套测试**：`test_frozen_config_dict_field_is_immutable`。

## §11 跨模块隐患

本节列出**单模块内独立都对、但跨模块组合产生隐患**的项目级风险。这些是项目演化过程中最容易堆积的"知识债"。

### 11.1 OOT / sim / live 三层逻辑一致性（CLAUDE.local.md 硬约束）

| 维度 | OOT（`pipeline_oot_evaluation.py`） | sim（`event_driven_backtest.py`） | live（`live_runner.py` + `live/risk.py`） |
|---|---|---|---|
| 成交时刻 | `entry_datetime`（候选已对齐到 next bar） | next_open / next_bar 内 trigger | broker 报单回报 |
| slippage | `slippage_pct_per_trade=0.0001`（pct）  | `slippage_ticks=1.5` 通过 cost_fn | broker 真实成交差 |
| commission | `commission_pct_per_trade=0.0002`（pct） | cost_fn 计算 | broker 真实手续费 |
| 涨跌停 | `feature_is_limit_up_close` 列 | `_hit_price_limit` 推断 OHLC | broker 拒单 |
| margin | `margin_rate=0.12 × notional` | **未计算** | broker 保证金 |
| leverage cap | `max_total_leverage=2.0`（名义口径） | 无 | 通常无（broker 自行约束） |
| 风控规则 | `RiskThrottle` 4 级 + caps | 无 | `RiskGuard` 4 条规则 |
| pyramid 加仓 | `PyramidManager` 三条件 | 单仓位 | broker 报单顺序决定 |
| trailing 止损 | `simulate_trailing_exit` ATR-based | 无（策略侧自行实现） | broker 不持有 trail；策略侧需在每根 bar 更新 |

**三层一致性问题清单**（综合 §4-§7 findings 总览）：

| # | 维度 | OOT vs sim | OOT vs live | sim vs live | 严重度 |
|---|---|---|---|---|---|
| C1 | 涨跌停判定 | ❌（特征 vs OHLC 推断） | ❌（特征 vs broker） | ❌（OHLC vs broker） | M |
| C2 | 风控状态机 | OOT 有 throttle，sim 无 | ❌（throttle vs RiskGuard） | sim 无，live 有 RiskGuard | **H** |
| C3 | margin 占用 | OOT 有，sim 无 | OOT 有，live 由 broker | sim 无，live 有 | M |
| C4 | trailing 实现 | 评估器内 simulate_trailing_exit | 由策略侧 on_bar 实现 | 由策略侧 + broker | M |
| C5 | leverage cap | OOT 检查 cap_lev | 无 | broker 检查保证金 | **H** |
| C6 | commission/slippage | pct 形式 | tick 形式 + cost_fn | 真实金额 | M |

### 11.2 离线训练 ↔ 在线推理 schema 一致性

- **风险**：[live/online_feature.py](cta/live/online_feature.py) 与 [feature/](cta/feature/) 离线计算函数**各自独立**。新增 feature 不强制同步。
- **现状**：无自动校验。
- **修法**：在 [live/tests/](cta/live/tests/) 加 `test_online_offline_feature_parity.py`，跑同一段 sample bars 在两个引擎，断言 column / dtype / value 一致。
- **关联 finding**：§7.5。

### 11.3 frozen dataclass 蔓延检查

- **巡检**：

  ```bash
  grep -rnE '\.[a-z_]+\s*=\s*' cta/portfolio_logic/ cta/config/ | \
  ```

- **风险**：如果有人手写 `"htf_missing"` 字符串而非用常量，未来重命名 BR_HTF_MISSING 时遗漏。
- **修法**：把所有字面量 `"htf_missing"` 引用替换为 `BR_HTF_MISSING`。

### 11.5 interval normalize 一致性

- **位置**：[portfolio_logic/config.py:normalize_portfolio_interval](cta/portfolio_logic/config.py:61) vs [strategy/skill_tight_range_backtest.py:normalize_interval](cta/strategy/skill_tight_range_backtest.py)。
- **现状**：两个 `normalize_*` 函数处理不同的别名集合。`portfolio_logic` 版本处理 `daily/d/1d/minute60/...`；`skill_tight_range_backtest` 版本处理存储路径相关别名。
- **风险**：interval label 在不同层之间转换时，若不显式调用 normalize，可能在比较时不匹配（"day" vs "daily"）。
- **现状结论**：OOT 评估器内部 [pipeline_oot_evaluation.py:148, 155](cta/model/pipeline_oot_evaluation.py:148) 都先 `normalize_portfolio_interval(...)` 再比较。✅
- **修法**：长期看应当统一为单一 normalize 函数，把存储别名和 portfolio 别名都收进去。

### 11.6 fit/predict 边界 — walk-forward purge

- **位置**：[pipeline_orchestrator_dataset_prep.py:_purge_by_exit_datetime](cta/model/pipeline_orchestrator_dataset_prep.py)
- **现状**（从 grep 结果）：使用 entry_datetime + exit_datetime 双指针 purge。

#### M-2.8 `_resolve_candidate_entry` 对 limit order trigger==极值的边界处理

- **位置**：[baseline_setup_detection.py:55-65](cta/strategy/baseline_setup_detection.py:55)
- **代码**：
  ```python
  if side == "long":
      if not np.isfinite(next_high) or next_high < trigger:
          return False, float("nan"), float(trigger)
      entry_price = max(next_open, trigger) if np.isfinite(next_open) else trigger
  ```
- **问题**：`next_high < trigger` ⇒ 不触发；`next_high >= trigger` ⇒ 触发。当 `trigger == next_high == next_open` 的极端情况（next_bar 开盘价正好等于触发价），返回 `entry_price = max(next_open, trigger) = next_open`，看起来 ok。但 `entry_price = trigger` 也合理；两种实现的差异在统计意义上很小，但**实盘 broker 通常按 trigger 价成交（GTC stop order）而非开盘价**。
- **修法**：明确选择"按 trigger 价成交"作为默认（与 broker 模型一致），仅在 `next_open > trigger`（gap-up open）时 fill 到 next_open。当前实现已经是 `max(next_open, trigger)`——其实是正确的"worst-fill"模型。**结论**：实现正确，但应当在 docstring 解释 fill 规则。
- **修法**：补 docstring 即可。

#### M-5.8 PyramidManager.decide_add_layer 不检查 base layer 是否已 exited

- **位置**：[pyramid_manager.py:254-256](cta/portfolio_logic/pyramid_manager.py:254)
- **代码**：
  ```python

  ```
- **问题**：`active_layers` 已经过滤掉 `exited=True` 的 layer。`base_layer = active_layers[0]`——但这是**最早未平**的 active layer，不是**初始** layer（layer_id=0 可能已 exited）。后续 `profit_atr` 用 `base_layer.entry_price` 作为基准，但 base layer 已被 trail 平仓的情况下，新 base 是更晚开仓的 layer，profit 基准时间被推迟。

  ```python
  base_layer = pos.layers[0]  # 始终锁定初始 layer
  ```

#### M-5.9 PortfolioState.add_position 不更新 tentative state

- **位置**：[portfolio_state.py:190-210](cta/portfolio_logic/portfolio_state.py:190)
- **代码**：
  ```python
  def add_position(self, pos: dict[str, Any]) -> None:
      # ... 更新 committed 计数 ...
      self.snapshot_for_allocation()
  ```
- **问题**：`add_position` 更新 committed 后调 `snapshot_for_allocation`——把 tentative 重置成最新 committed。这意味着在 `begin_allocation()` 后期间，**任何 `add_position` 都会清空 tentative 待决计数**。如果调用顺序是 begin → tentative_apply (×N) → add_position → commit_allocation，那 add_position 会把 tentative_apply 的 N 次累积全清掉。
- **影响**：实际使用模式下，`add_position` 在 OOT 评估器是"已确定开仓后写入"，发生在 commit_allocation 之后。但 API 名字暗示它也可能在 tentative 期间被调，那时会出 bug。
- **修法**：加 assertion：
  ```python
  def add_position(self, pos: dict[str, Any]) -> None:
      if self._tentative_total_positions != self._committed_total_positions:
          raise RuntimeError(
              "add_position called during pending tentative allocation; "
              "call commit_allocation or rollback_allocation first."
          )
      # ... existing logic ...
  ```
- **配套测试**：`test_add_position_raises_during_pending_tentative`。
