### H1. AST 巡检器对 `if-expr` 字面量盲区

**文件**：[cta/model/tests/test_pipeline_oot_evaluation.py:157-188](../../model/tests/test_pipeline_oot_evaluation.py)

**问题**：`_extract_block_reason_literals` 有三层扫描：

1. AST 扫 `Assign` 节点，target 是 `Subscript[..., "block_reason"]` 或 `"htf_block_reason"` → 覆盖 `selected.at[idx, "block_reason"] = "..."` 和 `record["block_reason"] = "..."`。
2. 正则 `\breason\s*=\s*"([a-z_]+)"` → 覆盖 `reason = "..."` 局部变量赋值。
3. 正则 `reason_list\.append\("([a-z_]+)"\)` → 覆盖 `reason_list.append("xxx")`。

但 [interval_gate.py:230](../../portfolio_logic/interval_gate.py)、[interval_gate.py:236](../../portfolio_logic/interval_gate.py) 是：

```python
reason_list.append("" if ok else "htf_opposite")
```

外层调用形式不匹配第 3 条正则（`append("xxx")` 形式），里面的 `"htf_opposite"` 也不是顶层 Constant 赋值，所以 **`htf_opposite` 字面量不会出现在 `seen` 集合里**。

**当前不破坏正确性**：测试断言 `seen - canonical == {}`，只检查"是否有未在白名单的 reason 被 emit"，`seen` 漏一个不会失败。`htf_opposite` 仍在 `_CANONICAL_BLOCK_REASONS` 白名单里。

**真正的风险**：未来若有人提交：

```python
reason_list.append("typo_block_reason" if ok else "")
```

测试会因为正则不匹配而**静默放过 typo**。

**建议修法**（10 行 diff）：在第 3 步之后追加一个 AST 扫，专门遍历 `ast.Call`，凡是 `func.attr == "append"` 的，把 args 里所有 `ast.Constant(str)` 收入 found（包括 `IfExp.body/orelse`）：

```python
for node in ast.walk(tree):
    if not isinstance(node, ast.Call):
        continue
    if not (isinstance(node.func, ast.Attribute) and node.func.attr == "append"):
        continue
    for arg in node.args:
        for sub in ast.walk(arg):
            if isinstance(sub, ast.Constant) and isinstance(sub.value, str):
                if sub.value:  # 跳过 ""
                    found.add(sub.value)
```

**优先级**：High。属于"巡检测试本身的盲区"，已经在文档 §21.3 列为必加测试，盲区会让巡检失效。

### H2. Fix-A 在单 interval 跑批时把 LTF 当成自己的 HTF

**文件**：[cta/model/pipeline_oot_evaluation_source.py.txt:601-627](../../model/pipeline_oot_evaluation_source.py.txt)

**问题**：Fix-A 的窄化逻辑会把 `htf_intervals=("day","60min")` 在 `--interval 60min` 单跑时窄化成 `("60min",)`。此时 HTF gate 实际只看 60min 自身的 regime label —— **它不再是 higher timeframe gate，只是个"自我一致性 gate"**。

```python
narrowed_cfg = dataclasses.replace(
    pl_cfg.interval_gate,
    htf_intervals=tuple(ref_intervals_seen),  # 如 ("60min",)
)
htf_gate = HtfGate(narrowed_cfg)
```

这是 Fix-A 已知设计权衡（plan §8 R1 也列了）。METAL day 案例下，"day 作为自己的 HTF"语义上还算说得过去（日线 regime → 日线候选）。但 60min/30min/15min 单跑批时，这种"自我一致性 gate"价值很低，几乎等同关掉 HTF gate。

**当前覆盖**：

- `logger.info("HTF intervals narrowed from %s to %s ...")` 输出窄化前后的 intervals — 但 INFO 行往往被淹没在 batch log 里
- 文档 §6.3 已经在「单 interval 跑批 checklist」里说明
- 未提示用户「实际效果等同 HTF gate 弱化」

**建议修法**（5 行 diff）：当窄化后 `len(ref_intervals_seen) == 1` 时，额外打一行更显眼的 WARNING：

```python
elif set(ref_intervals_seen) != set(configured_intervals):
    narrowed_cfg = dataclasses.replace(...)
    htf_gate = HtfGate(narrowed_cfg)
    logger.info("HTF intervals narrowed from %s to %s ...", ...)
    if len(ref_intervals_seen) == 1:
        logger.warning(
            "HTF gate narrowed to single interval %s — this degenerates to "
            "self-consistency gate (no actual higher-timeframe filtering). "
            "Pass htf_reference_df=<higher-interval-pred> for true HTF semantics. "
            "See cta/docs/block_reason.md §6.",
            ref_intervals_seen[0],
        )
```

**优先级**：High。不影响业务正确性，但用户不知道这点会以为"HTF gate 通过 = 该方向被高时间框架确认"，实际只有自己确认自己。

### M1. `_log_block_reason_distribution` 对 `__executed__` 标记的依赖性

**文件**：[cta/model/pipeline_oot_evaluation_source.py.txt:28-50](../../model/pipeline_oot_evaluation_source.py.txt)

```python
reason_series = (
    trade_df["block_reason"]
    .fillna("")
    .replace("", "__executed__")
)
```

**问题**：用 `"__executed__"` 作为"非阻塞"的 sentinel 字符串混入 `block_reason` 列做 `value_counts`，确实让 INFO 日志可读（直接看到"成交占多少"），但有副作用：

1. 如果 trade_df 已经被外部代码 mutate（如 unit test 直接读 trade_df 然后写测试断言），`block_reason` 列就会被改成 `__executed__`。这里用 `reason_series` 中间变量，本地变量不影响 trade_df，**目前是安全的**。
2. 把 `__executed__` 当 reason 字面量，跟 canonical 集合产生「概念冲突」（`__executed__` 不是 block_reason，是"无 block_reason"的反向 sentinel）。文档 §21.1 没明确说明这点，将来读 log 的人可能困惑。

**建议**：

- 已经是 fix-C 的核心呈现方式，**不必改**。
- 但在 [block_reason.md §7.2](../block_reason.md) 补一句："`__executed__` 是 logger 输出专用 sentinel，不是 canonical block_reason 字面量；它**不在** _CANONICAL_BLOCK_REASONS 集合里。"

**优先级**：Medium。文档完整性问题，代码无 bug。

### M2. Fix-A 与 `htf_state_cache` 缓存键的兼容性

**文件**：[cta/model/pipeline_oot_evaluation_source.py.txt:579](../../model/pipeline_oot_evaluation_source.py.txt)（声明）+ 后续 cache lookup 行

**问题**：`htf_state_cache: dict[pd.Timestamp, dict[tuple[str, str], dict[str, Any]]]` 的 key 是 timestamp，value 是 `compute_htf_state` 返回值。Fix-A 把 `htf_gate` 实例化时机推迟，但 cache **没绑定 gate**。如果未来同一个 `_evaluate_oot_real_execution` 调用内 `htf_gate` 实例被换掉（理论上不会，目前不会），cache 会跨 gate 共用，可能 stale。

**当前实际安全**：`htf_gate` 在循环开始前定型，循环内不再变化。`htf_state_cache` 只在该 gate 生命周期内有效。

```bash
grep -n "htf_state_cache" cta/model/pipeline_oot_evaluation_source.py.txt
```

**已验证**：tests `test_htf_intervals_narrowed_when_only_day_available` / `test_htf_gate_disabled_when_reference_has_no_overlap` 覆盖了"gate 在循环开始前被设置成 None"的路径，没有发现 cache 误用。

**优先级**：Medium → Low（已验证安全）。
