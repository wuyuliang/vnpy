## §0 怎么读这份文档

每条改进项固定 6 字段：

| 字段 | 含义 |
|------|------|
| **现状/问题** | 现在代码是什么样、为什么不对（带 `文件:行号`） |
| **alpha 影响** | 对「真实可交易 alpha」的影响——这是排序的唯一标准 |
| **实现锚点** | 改/新建哪些文件、复用哪些现有函数（`文件:行号`） |
| **改法** | 接口签名 / 字段 / 步骤级别的具体做法，不留歧义 |
| **验收** | 跑什么命令、加什么测试、期望指标 |
| **工作量** | 0.5d / 1d / 2-3d |

**优先级**：P0 = 切实盘前阻断 + 直接影响「这套策略到底有没有真 alpha」的判断；
P1 = 真实成本 / 稳健性 / 三层一致性；P2 = 工程卫生 / 技术债。

**不变量（任何条目都不能破坏）**：① 防特征穿越 / 标签泄露；② OOT/sim/live 同 cfg 同行为；
③ 风控 fail-open（缺数据不锁单）；④ 只改 `cta/**`；⑤ 历史回测产物（`cta/backtest`、
`cta/report/backtest`）只读不动。

## §1 当前系统能力快照（一句话）

模型 + 特征 + 风控组件（`cta/risk/` 16 个组件 / 257 测试）+ OOT 评估管线**测试完整、架构健康**；

低流动性护栏没在 OOT 生效）；**(c) live 落地最后一公里**（live 未接 RiskOrchestrator，
OOT/sim/live 三层 cfg 未强制一致）。这三块直接决定"回测好看 vs 实盘能赚"。

## §3 P0 — 切实盘前阻断 + 真 alpha 判断

### B1 live 接入 RiskOrchestrator（三层同 cfg 同行为）

- **现状/问题**：`cta/live/` 目录零引用 `cta.risk`（grep `from cta.risk` = 0）。
  [`cta/live/live_runner.py`](../live/live_runner.py) 只复用 `SimRunner`，下单路径不走
  风控编排。而 sim 已接（[`cta/sim/adapters/entry_gate_chain.py:116-120`](../sim/adapters/entry_gate_chain.py)
  调 `RiskOrchestrator.from_config`），OOT 也接了
  （[`cta/model/oot/pipeline_oot_evaluation_inputs.py:181`](../model/oot/pipeline_oot_evaluation_inputs.py)）。
  → **违反「OOT/sim/live 同 cfg 同行为」不变量**：实盘可能下出 OOT/sim 不会下的单。
- **alpha 影响**：致命。实盘风控与回测不一致 = 回测结论对实盘无效；也是合规/爆仓风险。
- **实现锚点**：`cta/live/live_runner.py`（下单 hook）；复用
  `cta/sim/adapters/entry_gate_chain.py:EntryGateChain` 整条链 + `RiskOrchestrator.from_config`；
  pre-trade 硬拒复用 `cta/live/risk.py:RiskGuard`（已存在）。
- **改法**：
  1. live_runner 构造时按同一份 `OotEvaluationConfig` 建 `EntryGateChain`（开仓）+
     `PositionEvaluator`（hard_stop）+ `RiskGuard`（6 条 `_BaseRule`）。
  2. on_signal → `chain.evaluate(candidate, state_provider, dt, original_lots=...)`；
     `passed=False` 直接不下单，`adjusted_lots` 作为最终手数。
  3. 凭据/路径从 config 注入，**禁止硬编码**（CLAUDE.local.md）。
- **验收**：新增 `cta/live/tests/test_live_risk_wire.py`：构造同一 cfg，断言 live 与
  entry_gate_chain 对同一 candidate 给出相同 GateDecision；CI grep `from cta.risk` 在
  `cta/live/live_runner.py` 必须命中（防回归）。
- **工作量**：1-2d。

### B2 OOT 收益质量诊断（剔除 top-N 笔后年化 + 集中度红线）

- **现状/问题**：OOT 报告有 symbol 排名 + `outlier_trades.csv`
  （[`cta/model/reporting/oot_report_views.py:117,172-176`](../model/reporting/oot_report_views.py)），
  但**没有「剔除最大 N 笔后的年化」「单笔/单品种收益占比」**这种揭示肥尾的指标。
  实测 `oot_20260529_050615`：单笔 EC0 = 总收益 8.9%，top20 笔 = 43%，top5 品种 = 42%——
  headline 的 37% 年化完全没体现这种集中度。
- **alpha 影响**：极高。这是「回测好看但不可交易」的头号信号。不加这层诊断，会反复被
  少数肥尾巨单（尤其低流动性品种）骗过去。
- **实现锚点**：扩 [`cta/model/reporting/oot_report_views.py`](../model/reporting/oot_report_views.py)
  + headline 写出 [`cta/model/reporting/oot_report_writer.py`](../model/reporting/oot_report_writer.py)。
- **改法**：在聚合 trade 表上新增并写进 `00_overview/headline_metrics.csv` + `09_diagnostics/`：
  - `annualized_return_pct`（现有）
  - `net_excl_top1_pct` / `net_excl_top5_pct` / `net_excl_top20_pct`（剔最大 N 笔后的总收益）
  - `annualized_excl_top20`（剔后年化——核心稳健指标）
  - `top1_trade_pnl_pct`（最大单笔占总 net）/ `top5_symbol_pnl_pct`（最大 5 品种占比）
  - `pnl_gini`（收益基尼系数，衡量集中度）
  - 阈值红线：`top1_trade_pnl_pct > 5%` 或 `top5_symbol_pnl_pct > 50%` → 在
    `executive_summary.md` 打 ⚠️ 标记。
- **验收**：对现有 bundle `oot_20260529_050615_cluster_both` 复算，断言能报出 EC0 单笔 8.9% +
  top20=43%；新增 `cta/model/tests/test_oot_concentration_diagnostics.py`。
- **工作量**：1d。

### B3 低流动性品种护栏在 OOT 生效 + symbol 级 liquidity floor

- **现状/问题**：[`cta/risk/guards/liquidity_floor_guard.py`](../risk/guards/liquidity_floor_guard.py)
  已实现（volume/spread/turnover 三指标），但只在 sim entry_gate_chain 跑，**OOT 评估完全
  不查流动性**。`symbol_disable_manifest.csv` 当前为空。结果：EC0（集运欧线，2023 上市、
  极不流动、单日波动巨大）那笔 +78,578 / 成本仅 29 元的成交在 OOT 里被当真实 alpha。
- **alpha 影响**：极高。低流动性品种的回测滑点失真会系统性高估收益；这类品种实盘几手就吃穿盘口。
- **实现锚点**：
  - 接入点 [`cta/model/oot/pipeline_oot_evaluation_inputs.py:181`](../model/oot/pipeline_oot_evaluation_inputs.py)（已建 orchestrator）；
  - guard [`cta/risk/guards/liquidity_floor_guard.py`](../risk/guards/liquidity_floor_guard.py)；
  - 持久名单 [`cta/feature/symbol_disable_manifest.csv`](../feature/symbol_disable_manifest.csv)。
- **改法**：
  1. OOT 候选表带上 volume/open_interest/spread（从 origin 数据 join），让 LiquidityFloorGuard
     在 OOT 也能拦低流动性 bar 的开仓（平仓放行，与现有 fail-open 一致）。
  2. 新增 symbol 级流动性下限 manifest `cta/config/liquidity_floor_manifest.py`：
     `{symbol: {min_adv_lots, max_spread_ticks}}`，缺省回退 cluster 默认。
  3. EC0（集运）、PG、SS 等已知薄品种初始写进 `symbol_disable_manifest.csv`，reason=
     `liquidity_too_low`，便于灰度恢复（复用现有 reason tag 机制）。
- **验收**：重跑 OOT，EC0 那笔 78k 巨单被 `blocked_liquidity_floor` 拦；总收益里肥尾贡献下降；
  新增 `cta/model/tests/test_oot_liquidity_floor.py`。
- **工作量**：1-2d。

### B4 walk-forward 多窗口稳健性闸门

- **现状/问题**：主体 `cta/model/` 无多窗口 walk-forward 稳健性测试，只在 skills 子包有
  [`cta/skills/ml_augmentation/tests/test_walk_forward_validation.py`](../skills/ml_augmentation/tests/test_walk_forward_validation.py)。
  当前 OOT 只看 2024-2025 一整段——TA0/L0 单次重训从 -15k/-11k 翻到 +18k/+10k 这种大摆动
  无法判断是真 alpha 还是 regime-fit。
- **alpha 影响**：极高。单段 OOT 漂亮极易过拟合；多窗口一致为正才是稳健 alpha 的最低证据。
- **实现锚点**：`cta/model/eval_only_cli.py`（加 `--walk-forward-windows N`）+
  `cta/model/eval_only_run.py`（多窗口循环 + 方差汇总）；复用 train 的
  `--max-walk-forward-windows` / `--window-mode` 切窗逻辑。
- **改法**：
  1. eval 支持把 OOT 期再切成 N 个滚动子窗（如 4 个半年窗），逐窗算 annualized / sharpe / MDD。
  2. 输出 `walk_forward_summary.csv`：每窗指标 + 跨窗 mean/std + `win_window_ratio`
     （多少窗为正）。
  3. 闸门：`win_window_ratio < 0.75` 或 `sharpe_std/sharpe_mean > 1.0` → executive_summary
     打 ⚠️「疑似单段过拟合」。
- **验收**：对现有 bundle 跑 4 窗，报出每窗收益 + 跨窗方差；新增
  `cta/model/tests/test_walk_forward_eval.py`。
- **工作量**：2d。

## §4 P1 — 真实成本 / 稳健性 / 一致性

### C1 成本模型升级：symbol 级佣金 + 冲击成本(ADV/参与率)

- **现状/问题**：[`cta/config/cost_manifest.py:31-69`](../config/cost_manifest.py) 只有
  cluster×interval 粒度（8 cluster × 6 interval）+ `INTERVAL_SLIPPAGE_MULTIPLIER`
  （day 1.0x → min 2.5x）。无 per-symbol 佣金（同 cluster 内 IF vs IC 手续费差很多）、
  **无冲击成本模型**（grep `impact/adv/participation` = 0）——大单滑点严重低估。
- **alpha 影响**：高。成本是 CTA 净收益的头号侵蚀项；分钟级 + 大单尤甚。低估成本 = 高估 alpha。
- **实现锚点**：[`cta/config/cost_manifest.py`](../config/cost_manifest.py)；成交成本应用点
  在 [`cta/model/oot/pipeline_oot_evaluation_inputs.py:resolve_per_row_cost_pct`](../model/oot/pipeline_oot_evaluation_inputs.py)。
- **改法**：
  1. `cost_manifest.py` 加 `COMMISSION_PCT_BY_SYMBOL: dict[str, float]` override（缺省回退 cluster）。
  2. 新增 `impact_cost_pct(order_lots, adv_lots, k=0.1) = k * sqrt(participation)`，
     `participation = order_lots / adv_lots`；ADV 从 origin 数据滚动 20 日算。
  3. `resolve_per_row_cost_pct` = 佣金 + 基础滑点×interval_mult + 冲击成本。
  4. 全部可通过 `--commission-mode global` 退回旧标量（保留退路）。
- **验收**：单测 `cta/config/tests/test_impact_cost.py`（参与率↑→成本↑、ADV 缺失 fail-safe
  回退基础滑点）；OOT 重跑后分钟路径 net_pnl 应下降（更保守）。
- **工作量**：2-3d。

### C2 per-(cluster,symbol) 分位阈值真正生效

- **现状/问题**：[`cta/risk/threshold/quantile_threshold.py`](../risk/threshold/quantile_threshold.py)
  H1 已修成 `max(base, label)`（不再下调 bond 严格阈值），但 `emit_pctl=True`（orchestrator
  默认）下输出仍是 `quantile_field` 字面值（p70→70.0），**manifest 里每个 (cluster,symbol)
  自己的 raw_q 分位数据没真正用上**。子系统①设计意图（按 symbol 自适应阈值）未达成。
- **alpha 影响**：中。不同 symbol 的 prob 分布差异大，统一 70pp 会误杀分布偏低的、放过分布
  偏高的；按 symbol 自适应能提精度。
- **实现锚点**：[`cta/risk/threshold/quantile_threshold.py:60-78`](../risk/threshold/quantile_threshold.py)
  + manifest [`cta/risk/state/score_quantile_manifest.py`](../risk/state/score_quantile_manifest.py)。
- **改法**：emit_pctl 模式下，用该 (cluster,symbol,interval) 的 raw_q（trade_filter_prob 在
  quantile_field 处的值）映射成「该 symbol 自身分布的 pctl 阈值」——即输出令"只放行该 symbol
  prob 分布前 (100-quantile)% 的候选"的等效 pctl。仍保持 `max(base, label)` 不下调 base。
  **防泄露铁律**：raw_q 只能来自 train+valid manifest，绝不在 OOT batch 现算。
- **验收**：扩 `cta/risk/tests/test_quantile_threshold.py`：不同 symbol 给不同有效阈值；
  manifest 缺该 symbol → fail-open 回 base。
- **工作量**：1d。

- **实现锚点**：`cta/model/eval_only_run.py`（dump 处）+ 新建测试。
- **改法**：

  2. 新增 `cta/run/tests/test_cfg_consistency.py`：构造 train+eval，断言核心字段

- **验收**：测试通过；故意改一个字段能被 drift_report 抓到。
- **工作量**：1d。

### C4 已实现 guard 接入 OOT eval

- **现状/问题**：[`cta/risk/orchestrator.py:from_config`](../risk/orchestrator.py) 已装配
  W7-W10 的 sizer，但 **guards（CrossClusterCorrelation / Liquidity / ConsecutiveLoss /
  SignalConcentration）是 `_BaseRule`，走 `RiskGuard`，OOT 批处理里根本没跑**。OOT 因此看不到
  cluster 集中度、连损冷却、信号并发等约束的影响。
- **alpha 影响**：中高。这些约束在实盘会减仓/拦单，OOT 不跑 = 高估收益（尤其黑色系联动、

  guards 在 [`cta/risk/guards/`](../risk/guards/)。
- **改法**：在 OOT 候选评估处增加「guard 批处理钩子」——按时间顺序回放候选，维护
  `open_positions_by_cluster_direction` / 连损 tracker / 当 bar 信号计数，逐条过 guard 链，
  被拦的写 `risk_block_reason`。需保证 OOT 与 sim 用同一 guard 实例语义。
- **验收**：OOT 报告出现 `blocked_cross_cluster` / `blocked_consecutive_loss` 等 reason；
  新增 `cta/model/tests/test_oot_guard_chain.py`。
- **工作量**：1-2d。

### C6 「可部署资金」收益口径（修分散化假象）

- **现状/问题**：当前年化按 222 腿（74 symbol × 3 interval）共用 1000 万名义算，净值曲线
  天然平滑 → MDD -3.55%、Calmar ~10，**不真实**（机构级 CTA 长期 Calmar 3-5 已很好）。
  报告没区分「名义收益」和「可部署保证金上的收益」。注：Calmar 假象来自**腿数/相关性**
  （分散化），与资金规模无关——改资金（见 C8）解决的是「保证金装得下」，本条解决的是「口径」。
- **alpha 影响**：中高。决定能不能上规模——分散化假象会让人误判容量与真实风险调整收益。
- **实现锚点**：[`cta/model/reporting/oot_report_writer.py`](../model/reporting/oot_report_writer.py)
  + headline。
- **改法**：headline 增列：`peak_margin_used`（峰值占用保证金）、
  `return_on_peak_margin`（净收益 / 峰值保证金）、`return_on_risk_capital`

### C8 回测资金 1M → 10M（贴近可部署规模）+ 校验 sizing 口径 ⚡quick win

- **现状/问题**：`initial_capital=1_000_000.0` 在 3 处 config 默认：
  [`cta/config/model_oot_eval_config.py:130`](../config/model_oot_eval_config.py)（主用）、
  [`cta/config/baseline_skill_suite_config.py:88`](../config/baseline_skill_suite_config.py)、
  [`cta/config/skill_tight_range_breakout_config.py:68`](../config/skill_tight_range_breakout_config.py)。
  当前 222 腿共用 100 万——单张股指期货保证金就 ~10-20 万，1M **根本装不下这么多腿**，
  notional / 保证金口径偏挤、不真实。
- **alpha 影响**：中（容量/真实性 + 业绩归因正确性）。
- **实现锚点**：上述 3 处默认值；消费点
  [`oot_report_writer.py:205-212`](../model/reporting/oot_report_writer.py)
  （资金曲线 + `total_ret = pnl.sum()/initial_capital` + 月度夏普）、
  `group_pool_aggregate.py:260`；sizing
  [`opportunity_ranker.py:136-138`](../portfolio_logic/opportunity_ranker.py)（notional cap 用 `equity`）。
- **改法**：3 处默认 `1_000_000.0 → 10_000_000.0`（**必须保持一致**，否则 return% 分母漂移）。
  **⚠️ 关键前置校验**：notional cap 用的是 `state.equity`（=initial_capital + cumsum(pnl)），
  不是固定 initial_capital。所以改资金对 return% 的影响**取决于 position sizing 是否随 equity 缩放**：
  - ① 若 sizing 随 equity 缩放（按 notional_pct × equity 开仓）→ pnl 同步 ~10x，
    `total_return_pct = pnl/capital` **基本不变**，只是绝对持仓/盈亏数更真实——**这是预期结果**；
  - ② 若 sizing 是 fixed-lot（每信号固定手数）→ pnl 不变、return% 直接缩 1/10，需重新解读所有
    历史 headline。
  → **先确认 sizing 模式**（看 opportunity_ranker / 下单 lots 计算），再改；改完**必须重跑一次 OOT**
  确认 return% 行为符合 ①。与 C6 联动但不等同：C8 调"基准资金大小"，C6 给"return-on-peak-margin 口径"。
- **验收**：3 处默认值=10_000_000；重跑 bundle 后 headline `initial_capital=10000000`、
  return% 行为符合 sizing 模式预期；`grep -rn "1_000_000" cta/config` 仅剩非 capital 用途。
- **工作量**：0.5d。

## §7 不变量提醒（实现任何条目都不能破坏）

1. **防泄露**：分位/排名/分布基准只能来自 train+valid（`exclude_splits=("test","oot")`），
   绝不在 OOT batch 内现算（参考 `build_from_predictions` / `_percentile_score` 现有写法）。
2. **三层同 cfg 同行为**：OOT / sim / live 必须由同一 `OotEvaluationConfig` 构造 orchestrator
   与 guard；新增字段都要落进 cfg_fingerprint。
3. **fail-open**：所有 guard / scaler / manifest 缺数据或异常 → 退回上一阶段、不锁单。
4. **真实成交**：成本、涨跌停、换月、流动性约束尽量贴实盘；宁可保守低估 alpha，不可乐观高估。
5. **cta/ 边界**：只改 `cta/**`；历史回测产物（`cta/backtest`、`cta/report/backtest`）只读不动。
6. **变更管理**：每条实现完成后更新 `cta/report/change_log.md`，含修改文件 / 运行命令 /
   结果位置 / 风险点。

## §8 一句话收尾

这套系统的工程骨架（模型 / 特征 / 风控 / OOT 管线）已经很扎实；**接下来最值钱的不是加新

是「能落地的 alpha」而不是「好看的曲线」。然后 B1 把 live 接上，就能从纸面走到实盘。
